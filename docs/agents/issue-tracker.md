# 本地规格与任务

默认使用项目本地文件，不自动创建 GitLab/GitHub 工单。项目规则及用户当前要求优先。

- 复杂任务的唯一规格：`.scratch/specs/<任务名>.md`，记录目标、范围、涉及仓库/工作区、可执行验收场景和证据。简单机械修改不要求建规格；未使用 to-tickets 的普通任务可直接在规格中维护简短清单。
- 使用 Matt `to-tickets` 时沿用原生本地格式：`.scratch/<任务名>/issues/<NN>-<slug>.md`，每票一个文件，按依赖编号，引用唯一规格，不再维护规格中的重复执行清单。每票包括 What to build、Blocked by（票号/标题或 None）、Status（初始 ready-for-agent）和验收条目；保持可独立验证的纵向切片。
- `implement-spec` 读取规格和上述票图，只领取所有阻塞票均已完成的 frontier；同一票只有一个状态来源。实际实现、测试和审查通过后填入证据并将 Status 改为 done，未满足验收不能关闭。更新 frontier 再领取下一票；本地完成不表示关闭远端工单或自动修改父规格。
- `to-spec` 的“发布”表示保存上述本地规格；`to-tickets` 的“发布”表示保存已确认的本地票。`code-review` 指定该规格与适用票文件、明确比较基线并包含本次未提交/新增文件。
- 只有用户明确指定远端工单系统及相应操作时才适配；不能将本地记录宣称为远端更新。GitLab CI 与交付继续遵守项目原规则。`triage` 的本地标签见 triage-labels.md；已完成状态为 done。
